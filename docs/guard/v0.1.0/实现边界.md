# 代码守卫 v0.1.0 实现边界

## 1. 建设背景

当前仓库已经具备 Go AST Code Guard、历史 baseline、Makefile 入口、本地 Git Hook 和 GitHub CI，但这些能力尚未组成覆盖 Root Go、Desktop Go、Frontend 和增量债务治理的统一门禁。现有守卫能够识别代码体量与复杂度，却不能充分判断 AI 生成代码是否可编译、可测试、已接入运行链路，或是否通过零碎文件、机械包装和复制粘贴规避指标。

v0.1.0 的工作是把现有能力组织成一套分阶段、可验证、可逐步收紧的代码质量体系。建设必须兼容当前业务开发和 484 条历史问题，不能要求先完成全仓重构。

## 2. 总体目标

代码守卫 v0.1.0 最终需要做到：

- 新增代码能够通过编译、构建、测试和必要的注册链路检查；
- 新增或修改代码不得引入新的结构硬门禁问题；
- 历史问题允许保持或下降，不允许恶化；
- 明确不可用的问题由 `error` 阻止；
- 启发式设计问题先以 `warning` 收集证据；
- 历史问题作为 `debt` 持续统计；
- 默认检查只读，baseline 只通过显式命令更新；
- 本地提供快速反馈，CI 提供不可绕过的最终结论；
- 不允许通过大文件、机械拆函数、一函数一文件、零碎包装或复制粘贴规避规则。

## 3. v0.1.0 包含的能力

v0.1.0 规划包含以下建设范围：

1. 固定规则分类、扫描范围、严重度、baseline 和豁免语义。
2. 将现有 Code Guard 改造成只读、可重复的增量比较器并接入 CI。
3. 将 Root Go、Desktop Go 和 Frontend 的基础验证纳入统一门禁。
4. 对新增生产代码应用更严格的结构 warning/error 阈值。
5. 检测占位、空实现、构建遗漏以及已知注册链路遗漏。
6. 识别碎片候选、重复代码和机械转发包装。
7. 对新增或修改行设置覆盖率要求，并对高风险代码使用更高阈值。
8. 建立 484 条历史债务的趋势、优先级、豁免到期和收敛机制。

## 4. v0.1.0 不包含的能力

以下内容不是 v0.1.0 的前置完成条件：

- 一次性修复全部 484 条历史问题；
- 仅为降低指标而进行全仓大规模重构；
- 用静态指标替代业务正确性、安全评审或人工代码评审；
- 自动判断所有插件、反射、序列化或外部 API 的真实调用关系；
- 对所有语言建立相同的 AST 规则实现；
- 将所有 warning 在首轮直接升级为硬门禁；
- 强制安装本地 Git Hook；
- 依赖本地 Hook 作为最终合并依据；
- 在本规划阶段修改守卫代码、业务代码或 CI。

## 5. 当前 Code Guard 基础

当前 Go AST Code Guard 默认扫描 `internal/`、`cmd/`、`scripts/`、`tools/` 下的生产 Go 文件，现有硬阈值为：

| 指标 | 当前阈值 |
|---|---:|
| 文件有效行数 | 800 |
| 函数有效行数 | 80 |
| 嵌套深度 | 4 |
| 圈复杂度 | 10 |
| 单包生产文件数 | 30 |

现有能力继续作为 v0.1.0 的起点，不另建一套平行守卫。

## 6. 484 条历史问题的处理边界

当前 baseline 包含：

| 类型 | 数量 |
|---|---:|
| 圈复杂度 | 394 |
| 超长文件 | 18 |
| 超长函数 | 51 |
| 嵌套深度超限 | 20 |
| 单包生产文件数超限 | 1 |
| 合计 | 484 |

处理边界如下：

- 484 条全部作为 `debt` 起点，不因 v0.1.0 启动而立即失败；
- 同一条问题实际值上升视为恶化并失败；
- 新增问题视为增量债务并失败；
- 条目消失或实际值下降允许通过，但 baseline 只通过显式命令刷新；
- 条目移动或改名必须区分“旧项消失、新项新增”和真实修复；
- 静态超限不等同于功能 Bug，治理前必须结合职责、调用链和测试；
- 当前逐项核实依据见 `docs/fix/2026-07-10-code-guard-484-findings-audit.md`。

## 7. 扫描对象边界

### 7.1 Root Go

- 包括 `internal/`、`cmd/`、`scripts/`、`tools/` 下生产 Go 文件；
- 应用结构、完整性、编译、测试、lint、race 和覆盖率规则；
- `_test.go` 使用测试代码规则，不套用生产文件碎片率和体量硬限制。

### 7.2 Desktop Go

- `desktop/` 是独立 Go 模块，必须从阶段 1 开始进入 build、vet、test 和 lint；
- 阶段 2 起进入 Go 结构与完整性扫描；
- Desktop 历史问题必须单独生成初始 debt，不得与 Root Go baseline 混淆。

### 7.3 Frontend TypeScript/TSX

- 阶段 1 先强制 build、typecheck 和 `test:all`；
- 阶段 2 起检测占位、空实现和未接入构建图；
- 结构阈值只在 TypeScript/TSX 等价度量经过验证后启用；
- 不用简单物理行数替代语法级有效行数。

### 7.4 测试代码

- 必须编译并运行；
- 不使用生产代码的文件碎片率硬门禁；
- 允许表驱动测试、fixture 和平台测试形成小文件；
- 重复测试数据可报告，但不能与生产逻辑重复使用同一严重度；
- 测试变化是完整性证据之一，不是唯一证据。

### 7.5 生成代码

- 通过标准生成标识或明确目录识别；
- 不参与结构、碎片和重复代码门禁；
- 仍必须参与所属模块的编译和构建；
- 生成器或模板本身属于生产代码，应接受守卫。

## 8. 结果等级定义

### 8.1 `error`

满足以下任一条件时阻止：

- 代码无法编译、构建或通过要求的测试；
- 新增结构指标超过 error 阈值；
- 历史 debt 恶化；
- 新增确定性占位或空实现；
- 已纳入规则的工具、命令、路由或配置缺少必要接入；
- baseline 被检查过程修改；
- 已升级为硬门禁的碎片、重复或覆盖率规则失败。

### 8.2 `warning`

用于存在设计风险但自动判断不能可靠定性的情况，例如：

- 结构指标超过 warning 线但未达到 error；
- 疑似碎片文件或纯转发包装；
- 导出符号缺少生产调用方；
- 接口只有一个实现；
- 生产代码变化但测试未变化；
- 重复代码达到观察阈值；
- 豁免临近到期。

Warning 必须进入报告和趋势统计。升级为 error 前必须有稳定样本和误报数据。

### 8.3 `debt`

用于启用规则前已经存在的历史问题。Debt 不阻止当前变更，但：

- 不得增加；
- 不得恶化；
- 必须有稳定身份和当前值；
- 必须进入趋势报告；
- 修复后应显式从 baseline 移除。

## 9. Baseline 处理边界

- 默认检查命令只读；
- CI 使用基础分支 baseline 与当前扫描结果比较；
- 当前工作区 baseline 不能成为唯一真相来源；
- baseline 更新使用独立命令，不与普通检查混合；
- 显式更新入口必须先只读比较基础分支；存在新增或恶化时拒绝更新，只允许写入已经确认的改善和消失；
- CI 检查前后验证 baseline 无工作区和暂存区差异；
- baseline 记录规则、文件、符号、位置、当前值和阈值；
- baseline 格式错误、重复 key 或版本不兼容必须失败；
- 改善不自动写回，避免检查命令产生隐式变更。

## 10. 豁免治理边界

每条豁免必须包含：

- 规则名称；
- 文件或符号；
- 豁免原因；
- 负责人；
- 创建日期；
- 到期时间。

豁免必须遵守：

- 只针对具体规则和最小范围；
- 不允许目录级永久关闭所有守卫；
- 到期后默认失败或要求重新审批；
- 进入版本控制并接受评审；
- 出现在 CI 报告和趋势统计中；
- 不能豁免编译失败、baseline 隐式写入或格式损坏。

## 11. 本地、pre-push 与 CI 职责边界

### 11.1 本地快速检查

- 面向当前改动提供秒级或短时反馈；
- 优先检查变更文件、相关包和只读 Code Guard；
- 不替代完整 PR Ready。

### 11.2 PR Ready：当前过渡门禁与 v0.1.0 目标态

#### 当前过渡期最小门禁

- 打开或更新 PR 前，先同步最新 `main-v3` 并解决冲突，再执行当前六项检查；
- 六项检查依次覆盖 Code Guard、baseline 已跟踪、baseline 工作区与暂存区无差异、Root Go vet 和 test；
- `make pr-ready` 只封装六项检查，不包含 `main-v3` 同步和冲突处理；
- 任一环节失败均不得打开或更新 PR；
- Code Guard 仍可能在改善时写回 baseline，后续 diff 检查负责失败关闭，因此当前门禁尚不等于默认只读门禁。

#### v0.1.0 最终完整 PR Ready

- 同步最新 `main-v3` 并解决冲突仍是执行完整验证前的流程前提；
- PR Ready 检查本身默认只读，不隐式更新 baseline；
- 执行 Root Go、Desktop Go、Frontend 和 Code Guard 全套要求；
- 与 CI 使用相同规则、阈值和验证入口；
- 允许开发者在推送前主动发现问题。

### 11.3 pre-push

- 作为可选的本地便利功能；
- 安装状态属于每个 clone 的本地配置；
- `--no-verify` 可以绕过，因此不能作为最终门禁；
- 应调用统一入口，不复制另一套规则。

### 11.4 CI

- 是不可绕过的最终门禁；
- 必须从基础分支获取比较基准；
- 必须使用只读检查模式；
- 必须生成结构化和可读报告；
- 本地未安装 Hook 时仍应得到相同质量结论。

## 12. 阶段职责边界

| 阶段 | 职责 | 不在本阶段处理 |
|---|---|---|
| 0 | 固定规则、范围、等级、baseline、豁免与现状报告 | 不写守卫代码 |
| 1 | 建立只读、跨模块、不可绕过的 CI 增量门禁 | 不将碎片和重复直接设为 error |
| 2 | 新增结构与实现完整性守卫 | 不处理全仓历史碎片和重复 |
| 3 | 碎片、重复和变更覆盖率 | 不要求一次性治理全部历史问题 |
| 4 | 历史债务趋势和分批收敛 | 不进行无测试的大规模机械拆分 |

阶段门禁为累积关系。阶段 2–4 的 `硬门禁` 章节只描述本阶段新增或收紧的项目，阶段 1 及之前已经生效的门禁必须继续执行，不能被后续阶段清单替代。

## 13. 禁止的规避方式

实施和治理过程中禁止：

- 把多个无关职责合并进更大的文件；
- 为降低函数行数机械提取无语义 helper；
- 创建 `helper2.go`、`misc.go`、`utils_new.go` 一类无清晰职责文件；
- 一函数一文件；
- 叠加纯转发包装；
- 复制已有逻辑后轻微改名；
- 手工提高阈值掩盖新增问题；
- 直接编辑 baseline 伪装修复；
- 使用永久豁免替代治理；
- 删除或弱化测试只为通过门禁。

## 14. 当前任务边界

当前任务只创建 v0.1.0 规划文档。不得：

- 修改 `scripts/code_guard`；
- 修改 `scripts/code_guard_baseline.json`；
- 修改 Makefile；
- 修改 Git Hook；
- 修改 GitHub Actions；
- 新增守卫代码或测试；
- 修改业务代码；
- 开始任何阶段实施；
- 提交、推送或创建/更新 PR。
