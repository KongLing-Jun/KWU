# 阶段 0：守卫规则定稿与现状基线确认

## 1. 阶段名称

守卫规则定稿与现状基线确认。

## 2. 阶段背景

当前 Code Guard 已经运行并持有 484 条 baseline，但扫描范围、结果等级、检查只读性、跨模块边界和豁免语义尚未形成统一契约。若直接增加规则，后续实现会在阈值、baseline 和 CI 行为之间反复调整。

## 3. 当前问题

- 当前默认检查可能自动写回 baseline；
- Root Go 之外的扫描边界未固定；
- `error`、`warning`、`debt` 尚未统一进入输出模型；
- 测试代码、生成代码、平台文件和 Frontend 的处理规则未冻结；
- 豁免缺少统一字段和到期语义；
- 484 条问题虽已逐项核实，但尚未转成后续阶段共同使用的治理输入。

## 4. 阶段目标

冻结 v0.1.0 的规则目录、扫描对象、阈值、严重度、baseline、豁免和报告契约，并形成可复现的当前仓库只读快照。

## 5. 非目标

- 不修改 `scripts/code_guard`；
- 不接入 CI；
- 不修改 Makefile 或 Hook；
- 不新增实际门禁；
- 不修复 484 条历史问题；
- 不创建新的 baseline 数据。

## 6. 前置依赖

- 当前 `scripts/code_guard` 和 baseline 可读取；
- `docs/fix/2026-07-10-code-guard-484-findings-audit.md` 已提供逐项核实结果；
- Root、Desktop、Frontend 的构建与测试入口可识别；
- 目标主分支和仓库模块边界已明确。

## 7. 输入条件

- 当前 baseline：484 条；
- 当前规则阈值：文件 800、函数 80、嵌套 4、复杂度 10、包文件 30；
- 当前 strict 扫描与 baseline 逐项一致；
- 当前扫描范围主要为 `internal/`、`cmd/`、`scripts/`、`tools/` 的生产 Go 文件。

## 8. 扫描对象

本阶段只定义、核实和记录对象，不扩大实际扫描：

- Root Go 生产文件；
- Desktop Go 生产文件；
- Frontend TypeScript/TSX；
- Go/Frontend 测试代码；
- 生成代码；
- 平台文件和 build tag 文件；
- PR 变更文件与基础分支快照。

## 9. 本阶段新增守卫

本阶段不新增运行守卫，新增的是后续实现必须遵守的治理契约：

- Finding 统一字段；
- `error`、`warning`、`debt` 统一语义；
- baseline 增量语义；
- 豁免必填字段和到期规则；
- 扫描范围矩阵；
- 阶段规则升级条件。

## 10. 规则定义

每条规则必须定义：

- 稳定规则 ID；
- 适用语言和代码类型；
- 计算方式；
- warning/error 阈值；
- 自动排除；
- baseline 是否适用；
- 可否豁免；
- 修复建议；
- 正例和反例；
- 从 warning 升级为 error 的条件。

## 11. 阈值

阶段 0 固定两组阈值：

### 当前历史规则

| 指标 | Error |
|---|---:|
| 文件有效行数 | 800 |
| 函数有效行数 | 80 |
| 嵌套深度 | 4 |
| 圈复杂度 | 10 |
| 单包生产文件数 | 30 |

### 阶段 2 新增 Go 代码规则

| 指标 | Warning | Error |
|---|---:|---:|
| 函数有效行数 | 40 | 60 |
| 圈复杂度 | 8 | 10 |
| 嵌套深度 | 3 | 4 |
| 函数参数数 | 5 | 7 |
| 文件有效行数 | 400 | 600 |
| 单包生产文件数 | 24 | 30 |

以上数值先用于 Root Go 和 Desktop Go。Frontend TypeScript/TSX 只有在语法级有效行、复杂度、嵌套和参数等价度量经过验证，并单独冻结适用阈值后才启用结构门禁；验证完成前只进入构建、typecheck、测试和确定性完整性检查，禁止直接套用 Go 阈值或物理行数。

## 12. 硬门禁

本阶段不启用新的仓库硬门禁。以下情况阻止进入阶段 1：

- 484 条基线报告不能复现；
- 规则阈值或扫描范围仍存在冲突定义；
- baseline 更新是否允许自动写入尚未固定；
- 豁免字段或到期行为未固定；
- Root、Desktop、Frontend 的职责边界未固定。

## 13. Warning

只读现状报告需要标记：

- baseline 与当前扫描不一致；
- 文件或符号定位漂移；
- 规则定义缺少正反例；
- 规则缺少明确适用对象；
- 计划作为 error 但尚无低误报证据的规则。

## 14. Debt 处理

- 现有 484 条全部标记为 Root Go 历史 debt；
- 按规则、文件、包、实际值和超限倍数统计；
- 不把静态超限直接标记为功能 Bug；
- 后续新增模块历史问题必须单独记录启用日期和起始快照。

## 15. Baseline 处理

### 15.1 当前过渡事实

- 当前打开或更新 PR 前，必须先同步最新 `main-v3`、解决冲突，再依次执行 AGENTS.md 规定的六项检查；任一失败均不得继续；
- `make pr-ready` 与六项检查一致，但不执行 `main-v3` 同步或冲突处理；
- 当前全量 `go run ./scripts/code_guard` 在 finding 改善时可能自动收紧并写回 baseline；
- 随后的 baseline 工作区和暂存区 diff 检查会捕获写回并令门禁失败，这是失败关闭的过渡措施，不是默认完全只读的目标语义。

### 15.2 本阶段处理方式

- 本阶段只读 baseline；
- 不运行会写回 baseline 的普通模式；
- 使用 strict JSON 输出做现状复核；
- 记录 baseline 版本、条目数、规则分布和当前提交；
- 固定“新增失败、恶化失败、改善允许、显式刷新”的后续语义。

## 16. 豁免方式

阶段 0 固定豁免最小字段：规则、路径/符号、原因、负责人、创建日期、到期日期。阶段 0 不新增实际豁免，也不使用豁免修正现状报告。

## 17. 本地触发方式

现状核实使用只读 strict 输出：

```sh
go run ./scripts/code_guard -- --strict --json
```

退出码 1 表示发现当前历史违规，不等同于扫描失败。输出必须保存为临时证据，不写回 baseline。

## 18. CI 触发方式

本阶段不修改 CI。阶段交付物需要明确阶段 1 的 CI job、基础分支 baseline 来源和只读验证顺序。

## 19. 失败输出格式

阶段 0 定义后续统一字段：

```text
severity rule_id rule_name classification file line symbol base current limit message remediation exemption exemption_expires_at
```

其中 `severity` 取 `error`、`warning`、`debt`；`classification` 取 `new`、`worsened`、`improved`、`resolved`、`debt`。`classification=debt` 只表示同 key、同值的历史保持项，此时 `severity=debt`。人读报告分别显示新增、恶化、改善、消失和历史保持。

## 20. 开发建议

- 以当前实现为起点，不平行重写另一套守卫；
- 规则契约先于代码组织；
- 稳定 key 不仅依赖行号；
- Go 与 TypeScript 可以使用不同分析器，但输出统一；
- 确定性规则和启发式规则分开管理。

## 21. 实施注意事项

- 不用默认守卫模式生成现状报告，避免 baseline 自动变化；
- Dirty 工作区只要不影响扫描，可记录但不能清理用户变更；
- 新阈值不能直接追溯应用到 484 条历史问题；
- 测试代码和生成代码不能与生产代码使用相同碎片规则。

## 22. 对应测试

本阶段验证的是文档和数据一致性：

- baseline 条目总数为 484；
- 五类数量为 394、18、51、20、1；
- strict 当前结果与 baseline key 和字段一致；
- 报告中所有路径和行号可定位；
- 扫描范围、等级和阈值在边界文档、总计划和阶段计划之间一致；
- Frontend 结构阈值的等价度量验证和独立冻结条件在后续阶段中保持一致。

## 24. 验收标准

- 规则分类没有重叠或冲突；
- 所有扫描对象都有明确处理方式；
- 所有严重度都有明确退出语义；
- baseline 和豁免行为可直接指导阶段 1 实现；
- 当前 484 条可复现且不被误称为 484 个 Bug；
- 后续阶段不需要临时改写总体原则。

## 25. 完成定义

阶段 0 文档全部完成并通过一致性检查，规则、范围、阈值、等级、baseline 和豁免语义均可作为阶段 1 的冻结输入。

## 26. 进入下一阶段的条件

- 阶段 0 完成定义满足；
- 阶段 1 的预期文件触点、命令和 CI 验证顺序明确；
- 不存在需要边实现边决定的核心语义。

## 27. 风险

- 规则定义过宽会在阶段 2、3 产生高误报；
- 将静态指标等同于业务缺陷会诱导机械重构；
- 未区分模块 baseline 会造成 key 和债务归属混乱；
- 未固定只读语义会让 CI 检查产生副作用。

## 28. 暂不处理事项

- 守卫代码实现；
- CI、Makefile 和 Hook 修改；
- 484 条问题修复；
- 覆盖率门禁启用；
- 碎片和重复代码扫描实现。
