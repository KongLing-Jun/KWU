# 任务 002：建立资产事件通知与缓存接口

## 目标与交付物

在云事件已完成权威刷新、作用域复核和 checkpoint 提交后，向 Desktop 投递不影响事件结果的资产变化信号；同一 Desktop 发起的真实订阅模型任务在终态结算成功写入权威余额缓存后，也复用该信号投递 `balanceChanged`。Desktop 合并信号并通过 Wails 唤醒前端，同时提供不联网的当前绑定资产缓存读取 API。

交付物包括：

- cloud 核心的可选 post-checkpoint 资产观察者。
- Desktop 生命周期内的 pending/dirty 合并通知器和 `cloud-assets:changed` 事件。
- 真实结算观察器在成功写入余额缓存后的同通知器唤醒。
- 返回完整绑定 scope、余额版本和套餐版本的缓存只读 DTO/API。
- 覆盖事件分类、失败隔离、生命周期、合并与只读契约的 Go 测试。

## 源码与调用链证据

- `internal/cloud/event_sync_application.go`
  - `apply` 当前顺序是 skip → dispatch → confirmScope → `CommitApplied` → recovery GC。
  - 余额、冻结、结算和套餐事件会刷新资产；支付与第三方同步事件不满足本通知契约。
  - `EventSyncApplicationDependencies` 是增加窄观察者的现有构造入口。
- `internal/cloud/event_state_repository.go`
  - `CommitApplied` 以完整 `BindingScope` 和事件版本保证 checkpoint 单调；观察者不能改变其成功语义。
- `internal/cloud/payment_application.go`、`subscription_application.go`
  - `BalanceApplication.View` 与 `SubscriptionApplication.View` 只读取当前完整绑定的最后确认快照。
  - `BalanceSnapshot` 已含 `Version`；Desktop 前端类型尚未声明该字段。
- `desktop/cloud_runtime.go`
  - `cloudRuntime` 是账号、资产和事件工作器的单一 Desktop 所有者。
  - `start` 建立 lifecycle context，`close` 取消并等待 worker；`runEventWorker` 当前只记录终态结果。
  - fixture runtime 构造事件同步 worker；real runtime 只构造同生命周期通知器并保持无事件 transport。两者复用通知器，但生产来源不同。
- `desktop/model_billing.go`
  - `desktopRemoteSettlementObserver.CreditSettlementObserved` 在云端终态结算已经持久化后读取当前账号，复核账号、套餐和任务的完整 binding scope，再调用 `runtime.assets.StoreBalance`。
  - 当前成功写入后直接返回；真实 runtime 保持 `Realtime=false` 且不构造 event worker，因此不会有后续云事件替它发出前端唤醒。
  - `StoreBalance` 对版本单调，返回当前最高权威快照；重复结算观察最多需要一次幂等唤醒，不得为判断“是否变化”增加竞态读取。
- `desktop/app.go` startup 先保存 Wails context，再启动 cloud runtime，可作为发送器绑定时点。
- `desktop/cloud_api.go`
  - `CloudRefreshAssets` 会走完整 Bootstrap 和远端恢复，不可复用于事件唤醒。
  - 现有 DTO 已包含账号完整绑定字段及套餐版本，余额后端别名已携带版本。
- Codegraph 影响面要求回归 `event_sync_application*`、`cloud_event_runtime_test.go`、`cloud_api_test.go` 和 real runtime composition。

## 必须保持的行为

- `CommitApplied` 仍是最后一个权威事件步骤；recovery GC 仍是提交后的尽力清理。
- 重复、旧版本、刷新失败、作用域变化和 checkpoint 失败事件不产生资产通知。
- fixture 事件工作器的启动、账号切换、取消和关闭语义保持不变；real runtime 继续不构造事件工作器。
- 真实 runtime 的 `Realtime=false` 能力声明保持不变；账户页挂载时的 `CloudBootstrap` 继续承担恢复和外部变化校准。
- 真实结算的远端账号读取、scope 复核、缓存写入及错误返回语义保持不变。
- 所有资产缓存读取都严格使用当前完整绑定 scope。

## 实现约束

1. 观察者是可选依赖、无错误返回；调用端隔离 panic。
2. 观察者只在 `CommitApplied` 成功后调用，分类固定为：
   - balance：`balance.updated`、`freeze.created`、`freeze.expired`、`settlement.completed`、`settlement.exception`。
   - subscription：`subscription.updated`。
3. Desktop 回调只做非阻塞入队；pending/dirty 位必须合并连续类别且保证最终状态可达。
4. `cloud-assets:changed` 载荷只含 `balanceChanged`、`subscriptionChanged` 两个布尔值。
5. 任意唤醒都要求前端读取余额和套餐组合快照；事件版本不得作为前端资产排序值。
6. startup 后绑定 Wails 发送器；shutdown 必须先停止 worker，再清除发送器并结束通知循环。
7. 缓存 API 返回当前 `profile_id`、`cloud_user_id`、`binding_generation`、可用余额快照和套餐快照；缺失快照按可选字段表达。
8. 缓存 API 只调用 `BalanceApplication.View` 和 `SubscriptionApplication.View` 或等价缓存仓库只读路径，不触发账号恢复、支付恢复或远端模型刷新。
9. 真实结算通知必须位于账号与完整 scope 复核、`StoreBalance` 成功之后；远端读取、scope 复核或缓存写入失败时不通知。
10. 真实结算复用 `assetNotifier.notify(cloud.EventAssetChanges{BalanceChanged: true})` 或等价窄入口；通知器为 nil、未启动、未绑定或已关闭时安全退化，不向结算路径返回通知错误。
11. 结算重试允许产生重复唤醒；不得新增落盘前读取来判断变化。现有 Desktop 合并和前端版本单调合并负责消化重复。

## 验收标准

- 六类成功资产事件仅产生对应类别，两个排除事件不通知。
- 重复、旧版本、任何前置错误及 checkpoint 失败均不通知。
- 观察者 panic、通知槽满和 Wails 未绑定不影响 checkpoint 或后续事件。
- 连续 balance/subscription 事件可合并，但最终载荷保留两个 dirty 类别。
- runtime 关闭后没有迟到发送；切换绑定时旧 worker 不污染新 worker。
- 真实结算余额写入成功时产生 `balanceChanged`；远端读取失败、scope 不匹配或写入失败时不产生通知。
- 通知器不可用、关闭或重复结算唤醒不改变结算错误语义，也不导致余额版本回退。
- 缓存 API 返回当前完整 scope 和资产权威版本，测试可证明零远端调用。
- 新 API 对不完整、过期或变化中的绑定失败关闭，不返回旧 scope 资产。
