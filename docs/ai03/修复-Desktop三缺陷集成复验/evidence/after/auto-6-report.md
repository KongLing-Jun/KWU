# 集成修复后 6 次默认/自动推理 Desktop 报告

## 结论

- A01–A06 使用同一锁定产品、持久 dev profile、Provider 与 `gpt-5.6-luna`；session meta 的 effort 为空，
  Desktop 选择器显示“自动”。六次均由真实 Wails Desktop 发起并在当前会话验收。
- 模型语义交付质量、最终正常完成、Desktop 实时 final 均为 6/6；切换会话 0、接受后重复回复 0，
  `DEF-002/008/009/010` 均未复现。
- 成本不理想：1,771,133 tokens、86 次模型调用、107 次工具调用、1,501.928 秒模型耗时、23 次审批。
  按 observation 的任一恢复事件计，只有 A02 无恢复直达；A06 达到 537,895 tokens，是本轮最大尾部。
- 与相同三任务、相同 repeat 1/2 的固定 low 样本相比，auto 在质量与完成稳定性持平的前提下，tokens
  高 60.57%、模型调用高 26.47%、工具调用高 16.30%、模型耗时高 49.82%、final 总耗时高 42.97%。
  本轮没有显示 auto 的成本优势。

## 主要问题

1. `FIND-L12-001` 在 A03/A06 以两种形式复现：固定 120 秒超时，以及活跃 HTTP server 导致 readiness
   拒绝。它是当前最大的可操作成本风险，应独立做 Windows 子进程/后台服务生命周期最小复现。
2. A01/A04 的 Windows 默认解码失败与 A05 的精确 receipt 拒绝均可恢复，但增加调用、审批和完成步骤。
3. A06 初稿违反 no-gradient，模型在交付前自行修正；成品冻结 grader 与 Playwright 桌面、390px、320px、
   焦点、reduced-motion、无 gradient 全部通过。这是模型策略波动，不是成品质量失败。
4. `TI-001` 在 A06 再现；错配状态未发生点击，重新激活 Wails 后继续，不计产品失败。
