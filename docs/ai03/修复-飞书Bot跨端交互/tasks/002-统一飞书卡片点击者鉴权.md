## 2. 目标与预期产物

飞书卡片回调保留真实点击者的全部可信 ID，并用“任一命中”完成白名单检查：

- `open_id`、`union_id`、`user_id` 任一已配置值都可识别同一授权用户；
- 卡片 `user_id` 继续只定位原请求者 session，不能替代真实点击者授权；
- 未授权点击者和缺少真实点击者 ID 的回调失败关闭；
- 保留白名单内其他群成员操作群聊卡片的现有协作语义；
- 不迁移配置，不改变 session key、群组白名单、Bot 所有权或其他平台规则。

## 4. 实现合同

### 4.1 可信点击者身份

- 为 `InboundMessage` 增加可选、向后兼容的 operator ID 集合；保留
  `OperatorID` 作为兼容主值，其他平台和现有构造无需迁移。
- Feishu adapter 只从已通过现有飞书签名/verification 校验的 callback
  `event.operator.operator_id` 和 `event.operator` 收集 `open_id`、`union_id`、
  `user_id`。
- 忽略空字符串，按固定顺序稳定去重；兼容 `OperatorID` 必须来自同一集合。
- `action.value.user_id`、chat/message/thread 字段和卡片内容不得进入 operator
  候选。缺少全部可信 operator ID 时不得入队，必须返回现有失败/警告结果。

### 4.2 Gateway 鉴权

- 有 operator 身份时，只用兼容主 ID 与可信别名的去重集合执行平台用户白名单检查；
  任一命中即通过，全部不命中即拒绝。
- 不得在 operator 集合全部不命中时回退 `UserID`；卡片请求者永远不能授权点击。
- 非卡片普通消息继续只检查 `UserID`；现有只提供 `OperatorID` 的内部构造保持行为。
- `AllowAll` 的通用语义保持，但 Feishu adapter 已在入队前拒绝缺少点击者的卡片。
- 用户通过后继续按现有 `ChatID` 检查群组白名单；白名单内其他实际点击者可操作
  群聊卡片，未授权用户不可操作。
- 日志只记录 hash、候选数量或命中结果，不输出原始飞书 ID、别名列表或卡片载荷。

### 4.3 路由与兼容

- `UserID` 继续采用 action 请求者 ID 优先、真实点击者兜底的现有规则，以找到原
  Ask/审批等待 session；不得改变 `Session()`、`BuildSessionKey` 或 mapping。
- 普通文本 `/answer`、`/approve` 继续按消息发送者和现有 session key 工作。
- QQ、微信及其他 adapter 不收集多 ID，仍走原有单值用户鉴权。
