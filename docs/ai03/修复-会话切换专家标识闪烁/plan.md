# 会话切换 Composer 标识布局稳定计划

## 1. 背景与问题

从无专家的普通会话切换到已保存专家或专家团的会话时，Composer 会先显示
`Craft` 或专家解析中状态，再显示目标专家。现有普通/解析中控件与最终专家控件的
宽度不同，内容变化同时触发工具栏重新排布，因此用户感知到整个文本编辑框闪烁。

此前候选实现建立了专家状态所有权、解析状态和发送门禁，但真实应用验收仍失败。
它只避免了错误身份直接复用，没有保证普通、解析中和专家状态具有相同几何尺寸；
因此没有满足最初的视觉稳定需求。

源码调查还确认推理强度在历史显示后的第二阶段异步读取。当前只有数据返回且模型
支持时才挂载约 92px 的控件，宽屏下会产生另一处可达的工具栏横向位移。

## 2. 基线与源码证据

- 修订基线：`origin/main-v3@f1777a582545d3146ec184a1a89c1f0a9c754910`。
- Codegraph 对该基线用于调用路径和影响面导航；关键结论已由主工作区源码、旧候选
  实现的实际 diff、任务记录和真实应用失败结果交叉确认。
- `.expert` sidecar、Controller 恢复和 `CurrentExpertForTab` 能返回目标身份；
  问题不是专家数据丢失。

| 状态/控件 | 来源与恢复时机 | 对本问题的结论 |
| --- | --- | --- |
| 专家/专家团 | `useExpertCatalog` 在目标 tab 生效后单独异步读取 | 后刷且宽度变化，是主要闪烁源 |
| 推理强度 | `loadSessionDataForTab` 历史阶段完成后再调用 `EffortForTab` | 后刷且新增固定宽度控件，需单独处理 |
| Plan、Goal、省钱、工具权限 | `TabMeta`/`Meta` 随目标 tab 元数据恢复 | 没有证据表明它们在目标元数据后独立迟到 |
| 模型 | tab/meta 提供标签，路由事实另行解析 | 模型槽位始终存在，当前未证明会新增布局占位 |
| 技能、连接器 | `composerCapabilitiesByTab` 的前端内存选择 | 不从历史会话异步恢复，不属于本次后刷路径 |
| 文本草稿 | `composerSessionKey` 驱动同一 Composer 实例切换草稿 | Composer 不是每个会话各挂载一个独立实例 |

当前宽屏 CSS 中，`Craft`/解析中 shell 约 132px，专家 shell 可达约 216px；中等
断点和窄断点也使用不同尺寸。推理强度 wrapper 只在 `hasEffort` 为真时挂载，宽屏
占用约 92px。两条路径都会改变同一行剩余空间和模型控件宽度。

## 3. 目标与非目标

### 目标

- 普通、解析中、解析失败、单专家和专家团使用同一断点下完全相同的外层槽位尺寸。
- 专家内容可以变化，但变化不得改变 Composer 外框、工具栏高度或相邻控件位置。
- 宽屏首帧即预留推理强度槽位；数据后刷只填充内容，不新增或删除布局占位。
- 保留目标身份所有权、迟到响应保护和发送门禁，避免视觉修复造成错误专家发送。
- 保持会话历史和 tab 的现有切换时序，不增加等待目标配置的加载阶段。

### 非目标

- 不要求专家名称、`Craft` 和解析文案视觉完全相同；只要求布局稳定。
- 不把所有 Composer 配置聚合成新的会话快照，也不为每个会话常驻一个组件实例。
- 不扩展 Go `TabMeta`、Wails 接口、Controller 或持久化 schema。
- 不把技能、连接器改为持久化会话配置。
- 不处理新建页模式、会话历史布局、Welcome、模型市场或其他加载体验。
- 不以动画、淡入淡出或延迟整页切换掩盖布局变化。

## 4. 验收标准

| ID | 场景 | 验收结果 |
| --- | --- | --- |
| AC-01 | 普通→专家/专家团 | `Craft`、pending/error 和最终专家/专家团的可见触发区（含清除按钮）总宽高、背景与边框占位相同；相邻模型控件与 Composer 外框不位移 |
| AC-02 | 专家/专家团→普通 | 内容可切换为 `Craft`，但专家槽位及相邻控件位置保持不变 |
| AC-03 | 专家 A→专家 B/团队 | 长短名称变化只在固定槽内截断，不改变工具栏几何尺寸 |
| AC-04 | 身份 pending/error | textarea 可编辑、发送被阻止；旧身份不能用于目标会话 |
| AC-05 | 身份 ready | 显示目标身份或普通 `Craft`，发送只注入目标专家语义 |
| AC-06 | 快速切换/显式 Set、Clear | 迟到结果不能覆盖最后目标；操作结果绑定其目标 tab |
| AC-07 | 推理强度加载 | 宽屏 loading、supported、unsupported 三态的 effort 外层槽位尺寸相同 |
| AC-08 | 紧凑断点 | 沿用现有隐藏策略，不因固定槽位挤出发送按钮或产生第二行 |
| AC-09 | 稳定态交互 | 专家菜单、清除、手动重试、模型、模式和发送行为保持可用 |
| AC-10 | 范围 | 后端契约、持久化、依赖、新建页和 code guard baseline 不变 |

## 5. 选定方案

### 5.1 复用专家状态正确性

复用旧候选实现中已由源码和测试支持的部分：

- 专家解析状态带目标 tab 所有权，只有 owner 匹配的 ready 选择可发送。
- 请求序列与目标 tab 同时匹配时才能提交结果。
- `SetExpertForTab`、`ClearExpertForTab`、回滚和乐观选择绑定明确目标。
- 单 surface 复用同一 tab ID 的导航意图仍需使来源身份失效。
- pending/error 允许编辑但禁止发送；失败沿用 Toast 和手动重试。

旧候选仅作为可选的实现证据和加速来源，不是执行依赖。Stage 2 任务合同必须独立写明
上述行为、保留范围和验证场景，使新执行者无需旧 worktree 或聊天记录也能完成修复。
若原专用实现 worktree 仍可用，优先逐 hunks 复核并复用已验证的代码与测试，再新增
`fix:` 提交；不 amend 或重写历史。若不可用，则从最新 `main-v3` 的独立 worktree
按同一任务合同重建，不改变验收标准。

### 5.2 固定专家槽位

- 为专家意图建立唯一外层 shell，普通、pending、error、专家和专家团共享。
- 各状态的可见触发区组合（背景、边框、主按钮及专家清除按钮）使用相同的固定总宽高；
  仅透明 shell 等宽不算满足验收。
- 以现有专家状态所需空间为基准，在各容器断点固定该总占位；普通及 pending 不再使用
  更短的独立尺寸。
- 专家名称在槽内省略，清除按钮包含在固定总宽度内。
- 内容替换不改变 `composer-meta__params` 的 flex 占用，也不改变模型槽位约束。
- 测试同时比较共同 shell 与可见触发区组合的总尺寸、背景和边框占位，不能只断言
  wrapper 等宽或“存在最大宽度”。

### 5.3 固定推理强度槽位

- 宽屏始终挂载 effort 外层 wrapper，并固定为现有约 92px 的布局占位。
- loading 或 unsupported 时不提供可聚焦的伪控件；内容为空或不可见，但 wrapper
  继续占位。
- supported 时在同一 wrapper 内挂载现有 `EffortSwitcher`。
- 现有紧凑断点继续隐藏整个 effort wrapper，因此窄屏不额外浪费空间。
- 不改变 `EffortForTab` 的请求时序、返回契约或模型能力判定。

## 6. 影响范围与兼容性

预计实现影响：

- `desktop/frontend/src/features/experts/controller/useExpertCatalog.ts`
- `desktop/frontend/src/App.tsx`
- `desktop/frontend/src/features/composer/ui/Composer.tsx`
- `desktop/frontend/src/styles/session.css`
- 邻近专家状态、发送门禁、响应式工具栏和推理强度测试
- 本计划对应任务完成回执

可能不再需要旧候选中的独立 pending 尺寸样式和只验证受限宽度的断言；删除或改写
它们属于本修复范围。后端、数据、依赖和迁移均不变。

## 7. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 固定专家槽位挤压模型或发送按钮 | 按现有三个容器断点分别固定，并覆盖边界宽度 |
| 不支持推理的模型留下空白 | 这是经确认的宽屏稳定性取舍；紧凑断点继续隐藏 |
| 内容虽等宽但仍有颜色变化 | 验收允许槽内内容变化，只拒绝外框和相邻控件位移 |
| CSS 断言通过但真实界面仍闪 | 在真实 Desktop 中逐帧/录屏观察，并由用户完成体感验收 |
| 为了简化而删除 owner/send 保护 | 任务合同明确禁止；保留现有竞态与发送行为测试 |
| 复用旧候选时带入无关复杂度 | 旧候选只作可选证据；逐 hunks 复核，只保留与任务合同直接相关部分 |

整体难度为低到中：视觉修正局部，主要审查风险是保留必要的专家正确性代码并避免
再次用“中性态存在”替代几何尺寸验收。

## 8. 回滚

固定专家/effort 槽位不涉及数据迁移。任务合同必须按实际实现基线写明回滚边界：
若复用已有 owner/发送保护，则视觉 `fix:` 可独立回滚且保留这些保护；若从最新
`main-v3` 重建完整切片，则回滚完整切片恢复该基线。两种路径都不得留下仅有部分
owner、竞态或发送门禁的混合状态。

## 9. 验证计划

### 自动化

- 专家行为：保留普通↔专家、A→B、快速切换、失败重试、Set/Clear 和发送门禁。
- Composer DOM：所有专家解析状态使用同一 shell；可见触发区组合总尺寸一致；长名称
  仍被槽内截断。
- 响应式 CSS：宽屏、中等和窄断点的普通/pending/error/expert 总占位、背景与边框
  占位一致，不能只验证透明 wrapper。
- effort：loading、supported、unsupported 始终挂载同一宽屏 wrapper；紧凑断点
  仍隐藏；切换内容不改变外层 class 和尺寸。
- 运行 `pnpm test:typecheck`、相关聚焦测试；应用稳定后运行 `pnpm test:all` 和
  `pnpm build`。

不修改 Go；若最终 diff 触发更广 PR Gate，按分类结果扩展验证。

### 真实应用验收

- 不设置 `KWU_CLOUD_FAKE` 或其他模拟云环境变量。
- 在真实 Desktop 中反复执行普通→专家团、专家团→普通、长短专家名称切换。
- 观察 Composer 外框、模型控件和发送按钮不横移；槽内文字/头像变化可见但可接受。
- 切换支持/不支持推理强度的会话，确认宽屏 effort 数据后刷不推动相邻控件。
- 使用紧凑宽度回归发送按钮可见和单行布局。
- 自动化无法代替细微闪烁的主观判断，最终由用户按上述场景确认体感。

### PR Gate

获得 PR 授权后，先同步最新 `origin/main-v3`，再执行项目规定的 common checks 与：

```powershell
node ./scripts/pr-gate.mjs --base origin/main-v3 --run all
```

任何必需检查失败时不得创建或更新 PR。

## 10. 后续关口

本计划修订获批并合并后，单独更新现有任务合同，以自包含方式明确应保留的行为、
测试场景和必须替换的视觉实现。任务文档合并并获得实现授权后，若原专用实现
worktree 可用则按复核结果继续修复，否则从最新 `main-v3` 创建独立实现 worktree。

如果实现证明模型槽位、Plan/Goal、省钱、技能或连接器也会在目标会话已稳定后新增
布局占位，必须带真实运行证据重新讨论是否扩面；当前不按推测纳入。
