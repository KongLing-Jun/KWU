## 2. 实现依据

- `todo_write` 成功才会成为最新 baseline；错误返回使整次列表更新保持原子未应用。
- `hasFailedCompleteStepRecoveryForTodo` 可以让一个项目不出现在 missing 中，但不会在同一
  调用因另一项目失败时部分提交前者。
- L02 因此只收到“S2 缺 complete_step”，未获知 S1 仍是 canonical `in_progress`。
- 成功 `complete_step` 自动推进 matched step，不会重放或提交先前失败的 todo payload。

## 3. 必需行为

1. 不修改 todo 原子性、recovery 授权条件或 canonical 推进规则。
2. `todo_write` description/schema 明确：
   - 新 completed 项应先成功调用 `complete_step`；
   - 成功签署由 host 自动推进；
   - rejected todo_write 的任何状态均未应用。
3. 单项和多项缺签署错误都包含：
   - “本次完整更新未应用”的明确表述；
   - ledger 最新成功 todo 的 completed/in_progress/pending 摘要；
   - 精确缺失项目；
   - 对该旧状态中仍未完成的目标逐项成功调用 `complete_step` 的动作；host 自动推进后，
     只有列表仍需其他变更时才重新发送完整列表。
4. 若没有成功 todo baseline，保持既有宽松兼容行为。
5. 错误内容保持简短、有界，不输出完整历史或 receipt payload。

## 4. 允许与禁止范围

允许修改：

- `internal/tool/builtin/todo.go` 及其聚焦测试
- `internal/evidence/evidence.go` 仅限复用/暴露现有最新 todo 摘要所必需的窄 helper
- `internal/evidence/evidence_test.go`
- `internal/agent/evidence_flow_test.go` 的精确组合回归
- 本任务回执

禁止修改：

- `advanceCanonicalTodo`、synthetic todo receipt、final-readiness 或 frontend
- failed-signoff recovery 的成功条件
- 失败 todo 的部分提交或自动重放
- 依赖、配置、PR gate、`scripts/code_guard_baseline.json` 和 `plan.md`

## 5. 验收与验证

必须覆盖：

- 单项缺签署：错误说明未应用、旧状态摘要和缺失项；
- 多项缺签署：所有缺失项仍可定位；
- L02 组合：S1 failed-signoff recovery 可用、S2 缺签署时只将 S2 视为 missing，但错误明确
  整次未应用且旧状态仍 `[I,P,P]`；
- S2 成功签署后 S1 仍保持旧 canonical `in_progress`；再成功签署 S1 后 host 自动得到
  `[C,C,I]`，不需要冗余 todo_write；
- 成功 todo、无 baseline 和既有批量恢复测试保持通过。

聚焦验证：

```powershell
go test ./internal/evidence ./internal/tool/builtin ./internal/agent -run 'Todo|FailedCompleteStep|BatchTodo' -count=1
```

随后至少运行 `go test ./internal/evidence ./internal/tool/builtin ./internal/agent -count=1`。
