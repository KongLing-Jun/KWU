## 2. 实现依据

- readiness 会先把 candidate 标为 `readiness_rejected_candidate`，保留在 session 和下一次
  模型请求，再发出 retraction 与 retry user message。
- Desktop 实时投影、历史、preview 和 copy/export 会移除该候选；此行为是现有显式合同。
- 当前 retry message 只要求修复 receipt 后继续回答，没有告诉模型旧候选不能作为用户
  可见交付。
- accepted final 只做非空检查；对自然语言做启发式语义 gate 风险高且不在本任务范围。

## 3. 必需行为

1. 保留 readiness 判定、候选 typed persistence、事件顺序和前端过滤行为。
2. 通用 retry message 明确说明：
   - 当前候选会从用户可见记录撤回；
   - 修复 host-observable receipts 后必须重新输出完整、standalone 的 final；
   - final 应重述结果、实质变更、验证和限制；
   - 不得只报告 receipt、todo 或“已完成” bookkeeping。
3. 保留并兼容 ask-tool 和 artifact-host-owned 条款。
4. 不要求重复已经成功的验证，不声称候选内容自动有效，也不自动拼接候选。
5. 不新增长度、关键词、相似度或额外模型判定 gate。
