# 专家提示重复注入修复计划

## 背景与问题

召唤专家会打开目标会话，并把一条可编辑的专家预设问题写入 Composer。用户删除该
问题并正常发送消息后，进入消息通道等非聊天页面，再返回原会话或复用已有空白会话，
已删除的专家问题会重新出现。复用空白会话时，问题会稳定留在无专家的新会话中。

稳定复现路径：

1. 召唤专家，在新会话中删除预设问题并发送普通消息。
2. 进入消息通道，再返回原专家会话；已删除问题稳定重现。
3. 清空问题，进入消息通道并新建对话，得到空白会话。
4. 再次进入消息通道并新建对话；复用该空白会话后，专家问题稳定写入且不消失。

## 基线与证据

- 实现基线：`origin/main-v3@d8fb8982`。
- Codegraph 用主工作区 `main-v3@70a645b8` 导航调用路径；实现 worktree 比该索引多出的
  提交仅涉及发布说明，所有关键结论已在 worktree 源码中重新确认。
- `App.tsx` 将 `composerInsertRequest` 保存在 App 状态中，专家选择后创建 `replace`
  请求，但没有消费回执或清理路径。
- `Composer.tsx` 仅通过组件内 `consumedInsertIdRef` 去重；非聊天页面卸载 Composer，
  重挂载后该 ref 重置，同一请求会再次执行。
- Composer 使用稳定会话身份作为 draft key。真正切换到新会话时空白 draft 可能覆盖
  短暂重放；`EnsureBlankTab` 复用已有空白会话时 key 不变，重放内容因此稳定保留。
- 后端空白复用明确排除已选择专家的会话；无专家新会话中的可见问题是前端插入请求
  泄漏，不是后端专家继承。

## 目标

- 每个 `ComposerInsertRequest` 在 App 生命周期内最多成功消费一次。
- Composer 卸载、重挂载或复用同一空白会话时，不重放已经消费的请求。
- 新请求仍能正常替换文本、插入技能或工作区引用。
- 新请求到达速度快于旧请求清理时，只允许清理 ID 匹配的旧请求，不丢失新请求。

## 非目标

- 不改变专家激活、隐藏 system prompt、模型请求或专家标签语义。
- 不改变 `EnsureBlankTab` 的空白会话复用策略。
- 不新增持久化 schema、后端接口、依赖或迁移。
- 不调整 Composer 草稿隔离、会话切换和非聊天页面布局。

## 方案

为 Composer 增加可选的 `onInsertRequestConsumed(id)` 回调。Composer 判定请求尚未消费
后，先记录本实例的 ID，再同步执行回调并按现有分支处理请求。App 提供稳定回调，只在
当前请求 ID 与回执 ID 相同时把状态清为 `null`。

保留组件内 ref 作为同一挂载实例的防重复保护；App 级清理负责跨卸载生命周期的一次性
语义。ID 条件清理避免旧回执覆盖随后到达的新请求。

## 风险与控制

整体风险低。改动不触及后端和数据，但 `ComposerInsertRequest` 也服务于技能、连接器、
业务场景和回退编辑，因此不能只验证专家入口。

| 风险 | 控制 |
| --- | --- |
| 消费回执过早导致请求未执行 | 回执与同步分支在同一 effect 中执行，并保留本地 consumed ref |
| 旧回执清掉较新的请求 | App 使用 ID 条件更新 |
| 其他插入入口不再生效 | 覆盖 replace、连续新 ID、卸载重挂载的组件测试 |
| effect 因回调变化重复执行 | App 回调使用 `useCallback`，本地 ID 去重继续生效 |

## 验收标准

- AC-01：专家问题首次选择后正常出现在目标 Composer。
- AC-02：删除后切到消息通道并返回原会话，问题不再出现。
- AC-03：已有空白会话被重复“新建对话”复用时，不出现旧专家问题。
- AC-04：消费回执只清理同 ID 请求；随后到达的新 ID 仍正常执行。
- AC-05：普通会话和空白会话不继承专家标签或可见专家问题。
- AC-06：前端相关测试、`pnpm build` 与项目 code guard 通过。

## 验证计划

- 组件测试：请求首次消费、父级清理、Composer 卸载/重挂载不重放、连续新请求可消费。
- 真实应用：按稳定复现路径验证原专家会话和复用空白会话均不再出现旧问题。
- 范围检查：`git diff --check origin/main-v3...HEAD`、EOL、实际 diff 和前端构建。
- 若后续获得 PR 授权，先同步最新 `origin/main-v3`，再执行完整 PR Gate。

## 回滚

回滚本修复提交即可恢复原行为；无数据迁移或持久化清理要求。
