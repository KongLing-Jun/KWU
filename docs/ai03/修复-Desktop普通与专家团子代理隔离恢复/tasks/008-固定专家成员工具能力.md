## 问题与根因

专家团宿主已把固定 `member_name`可信映射为同一个 `subagentRef`，但模型仍能在每次 `task`中提交
不同的 `tools`白名单。`TaskTool`先按当次参数建立 Registry，再由 `SubagentStore.validateMeta`比较
持久化的 `ToolScope/ToolSchemaHash`。因此成员先做只读调查、后做写入修复时，续写会被正确但突兀地
拒绝为 `uses a different tool scope`。

严格校验不是缺陷；缺陷是专家层同时承诺固定成员 Session，又把该 Session的能力交给每个任务重选。

## 目标与边界

1. 专家团模型不再逐 task选择 `tools`；成员始终继承完整的子代理安全工具默认值。
2. 普通和专家调用继续共用现有 `TaskTool`、Registry、模型设置、SubagentStore和续写校验。
3. 普通 `task`的工具白名单、模型/推理强度覆盖和明确 ref续写保持现状。
4. 不迁移旧资料；不放宽工具 scope/schema校验；不处理成员栏视觉或其他验收问题。

## 实现合同

- `withExpertTeamTaskMemberSchema`从专家模型可见 schema移除 `tools`，继续隐藏 `continue_from`。
- `withExpertTeamMemberIdentity`在可信映射层删除输入中的 `tools`后再调用同一个 inner `task`，防止
  旧缓存 schema或直接调用绕过可见 schema。
- 不新增专家专用 Registry。`tools`缺省时复用 `TaskTool.buildSubReg`当前默认：继承父 Registry后应用
  既有 Subagent边界，排除创建孙代理和其他元工具。
- `model/effort`、预算、并发、父取消、计费、wait/stop、成员绑定和历史恢复均不改。
- 同版本且工具配置不变时重启后可续写；真实应用/MCP/插件/schema变化仍由 metadata严格拒绝，旧
  历史只读保留。

## 验收标准

- 专家 `task` schema不含 `tools`和 `continue_from`，仍含白名单 `member_name`。
- 即使调用参数带窄 `tools`，inner task收到的参数也不含该字段。
- 同一成员先完成只读检查、再执行写入修复，复用同一 `subagentRef`且不再出现 tool scope错误。
- 普通 task schema和显式工具白名单行为不变。
- 不放宽 `SubagentStore`的 scope/schema/model/actor严格校验。
- 专家 child仍无 `task/read_only_task/parallel_tasks`等嵌套代理能力。
