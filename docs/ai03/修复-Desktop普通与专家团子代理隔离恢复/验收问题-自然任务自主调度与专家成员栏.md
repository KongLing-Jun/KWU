# 验收发现问题：自然任务自主调度与专家成员栏

## 1. 文档地位

本文记录任务006在真实自然语言任务下的新一轮 Desktop 验收。此前使用“必须调用 task、指定成员、
指定返回标记”等高度限定 prompt 的结果，只能证明指定代码路径可运行，应降级为定向链路冒烟测试，
不能证明主 Agent 能自主完成真实专家团调度。

本轮只记录事实、用户影响和待确认边界，不预先指定修复方案。原始用户 prompt 只有：
`给我做一个贪吃蛇`。

## 2. 验收证据

- 用户导出：`C:\Users\ai03\Downloads\Global - 给我做一个贪吃蛇.md`。
- 父 Session：`20260807-082540.895620500-gpt-gpt-5.6-luna.jsonl`。
- 截图：
  - `codex-clipboard-b3e55bbf-b5d1-4c25-a56d-c0abf1752ecd.png`；
  - `codex-clipboard-9093040b-5e26-4ccd-b4d9-1f73dc06da00.png`。
- 运行环境：最新任务006开发构建，专家团模式，`gpt/gpt-5.6-luna`。

父 Session 共 45 条持久消息。第 3 至 43 条 assistant 消息均只有一个 tool call，`content`为空；
第 45 条才是最终自然语言回复。父 JSONL 没有持久化 reasoning 字段或中间 assistant 文本。

## 3. 问题一：主会话几乎只有工具调用

### 3.1 现象

主 Agent 从收到请求到最终交付之间，页面主体几乎全是 todo、task、wait_task、complete_step 和
verify_artifact 等工具卡片。用户看不到主 Agent 对目标的简短理解、当前安排、为何委派、等待期间状态、
发现风险后的处理决定等过程说明。

### 3.2 边界更正

这里需要的是用户可见的进度叙述和关键决策摘要，不等同于展示模型私有思维链。现有证据能确认父
Session 没有中间 assistant 文本，但仅凭持久 Session 还不能断言 Provider 从未产生过临时 reasoning
流；如需判断流式 reasoning 是否被前端丢弃，还要结合运行事件日志复核。

### 3.3 原始 SSE 对照结论

已对同一 `gpt/gpt-5.6-luna`兼容接口完成无副作用 A/B 探测；请求只声明一个不会实际执行的虚拟工具，
不把密钥或完整模型内容写入文档。

第一组普通工具提示验证：省略 `reasoning_effort`时响应没有 reasoning 字段；显式传
`reasoning_effort: high`后，同一接口返回标准 `reasoning_content`。这排除了 Reasonix 前端与
`reasoning_content`解析器整体失效。

第二组使用接近真实专家团的 system prompt、原始用户句子“给我做一个贪吃蛇”和单个 `task` schema：

| 请求 | 普通 content | reasoning_content | usage reasoning tokens | finish |
|---|---:|---:|---:|---|
| auto（省略 effort） | 0 字符 | 0 字符 | 47 | tool_calls |
| explicit low | 0 字符 | 50 字符 | 23 | tool_calls |
| explicit medium | 0 字符 | 45 字符 | 28 | tool_calls |
| explicit high | 0 字符 | 43 字符 | 49 | tool_calls |

两次都只生成一个逻辑 `task`调用；SSE 中一百余个 tool-call event 是同一调用参数的流式碎片，不是
一百余次工具调用。

**确认结论**：模型在 auto 下确实消耗了内部 reasoning tokens，但网关没有把推理文本作为
`reasoning_content`暴露。当前 Session effort 是 auto/空值，Provider 也没有 `default_effort`，因此
Reasonix请求会省略 `reasoning_effort`。显式 high 能恢复可展示 reasoning，说明不是 UI 丢失或字段
协议不兼容；补测 low 与 medium 也都返回标准 reasoning_content，因此不需要为了显示推理而强制
使用 high。表中 token/字符数来自各一次最小探测，只证明字段行为，不作为不同 effort 的质量、成本
或延迟基准。所有显式 effort 场景普通 content 仍为 0，证明“可见 reasoning”和“主 Agent主动输出
过程叙述”是两个独立产品问题。专家团不得覆盖会话明确选择的 effort。

### 3.4 已确认的 Composer 交互边界

- 保留既有 `auto` 运行时语义：当前会话不提供显式 effort 覆盖，继续由模型、Provider 及既有
  `default_effort`链决定，不因专家团模式改变。
- UI 继续使用“自动”称呼，与设置页“子智能体推理强度”一致；`low / medium / high`分别显示为
  “低 / 中 / 高”。可用等级仍来自当前模型能力，不删除既有自定义或更高等级。
- 不新增设置页“主 Agent 默认推理强度”。当前会话继续通过 Composer 调整，已有 session-local
  effort 保存、恢复和请求链不变。
- 将当前分离的模型与 effort 控件收敛到同一个模型选择入口；Composer 常驻区只显示紧凑的
  “模型名 · 当前强度”。展开后的一级面板只显示“模型”和“推理强度”两行，分别进入独立二级
  选择面板；解释文字只在二级面板或提示中出现。

这项修改只解决入口分散、紧凑布局隐藏 effort 和原始英文等级难理解的问题；它不会伪造 Provider
没有返回的 reasoning，也不把“自动”解释成最低档或无思考。

当前实现已复用既有模型目录、session-local effort 回调和 `AnchoredPopover`。一级、模型二级、
推理强度二级均已通过聚焦测试与真实 Desktop 检查；面板切换会在浏览器绘制前同步重测浮层位置，
避免二级面板因高度变化先出现在 Composer 下方、下一帧再跳回上方。

### 3.5 已确认的可见工作更新合同

- 只调整 Desktop 顶层父 Agent：基础父 Agent、单专家父 Agent和专家团主专家使用同一规则；child
  Agent 保持现有独立提示词，不要求对用户叙述过程。
- 非简单工作在首次工具/委派前、证据改变方案时、委派或长耗时结果返回后、最终交付前给出简短的
  普通 assistant 文本，说明目的、结果和下一步。
- 不展示私有思维链，不逐项播报工具，不重复工具输出，不给简单问答增加固定套话；工具运行期间由
  既有卡片反馈，不新增定时心跳。
- 复用普通 `content`的实时显示、父 Session 持久化和历史恢复，不新增前端协议或运行时硬性重试。
- 策略在 Desktop 本地场景 prompt 装配，不修改云端专家资源；旧 Session prompt 不迁移。

### 3.6 用户影响

长任务看起来像工具执行器而不是主专家在主持工作；大量工具卡片没有叙事连接，用户难以理解当前
阶段、委派依据和失败后的恢复动作。

## 4. 问题二：串行约束在模型与用户之间形成失败回路

### 4.1 实际顺序

1. 主 Agent 调用 `task`拉起“代码审查专家”，工具返回 running，并明确提示使用 wait_task/stop_task。
2. 第一个 child 尚在运行时，主 Agent 立即申请再次调用 `task`拉起“测试策略专家”。
3. 用户完成第二次工具批准后，运行时才拒绝：
   `a persistent sub-agent task is already running in this parent turn; use wait_task or stop_task before starting another`。
4. 主 Agent 随后对第一个成员连续调用三次 wait_task；完成后才重新拉起测试专家。

### 4.2 已确认边界

- 全局拒绝第二个持久 task 是此前为收紧父 turn 计费生命周期增加的保守门禁，不是 Session 或 jobs
  manager 的固有限制；既有 SubagentStore 已能锁住同一 ref，jobs 和父计费 barrier 也能持有多个 job。
- 正确边界是同一 ref 同时最多一个 running turn、同一父 turn 最多四个不同 ref。独立成员可并发，
  有依赖的成员由模型先 wait 前置结果再启动；父 final/结算仍必须等待所有必需 child 收口。
- 工具批准继续逐 task 使用既有权限合同；用户选择 Session 级授权后，同一 Session 后续 task 不重复
  提示。运行时不新增批量批准 UI、队列或第二套调度器。
- 本轮工具调用偏多不只来自串行执行，还包含 wait 轮询、complete_step evidence 重试、同一成员
  tool scope 不同导致的续用失败与重新拉起；需要分别归因，不能全部算作模型冗余。

### 4.3 相关续用异常

发布检查后，主 Agent尝试让原“代码审查专家”修复问题时，首次调用失败：
`subagent reference ... uses a different tool scope`；随后重新调用才成功。该行为会让“同一专家连续
Session”与“每次任务工具范围可变化”发生冲突，也是调用次数和成员状态异常的组成部分。

任务007新构建的自然复验再次独立命中该边界。父 Session
`20260807-121418.246063500-gpt-gpt-5.6-luna`已成功并发完成代码审查、测试策略和发布风险三个只读
child；主专家随后让发布风险顾问或测试策略专家使用写工具做必要修复时，两次分别返回
`uses a different tool scope`。这证明它不是旧的父级单 task 门禁造成，也不能由多 task 并发修复
顺带解决。已确认固定成员不允许逐 turn选择能力：专家 wrapper省略 `tools`，让成员首次创建和后续
续写都走现有完整子代理安全工具默认值；底层严格 identity校验不放宽。

这不是第二套调度器：普通与专家仍共用 `TaskTool`、Registry、模型设置和 SubagentStore；专家层只做
可信成员名到 ref的映射。普通 `task`的逐任务工具白名单保持不变。不迁移旧资料，同版本/同配置重启
必须恢复；真实工具或 schema变化时允许拒绝续写并保留旧历史只读。

### 4.4 多 task 修复后复验

- 独立场景：自然 prompt 未指定工具、成员或步骤；同一父 turn 成功拉起代码审查、测试策略和发布
  风险三位成员，并以一个 `wait_task`统一等待，旧的第二 task 拒绝未再出现。
- 依赖场景：自然 prompt 明确“先审查，等结论后再据此设计回归测试”；父 Session
  `20260807-122125.508752500-gpt-gpt-5.6-luna`先启动并等待代码审查 child
  `sa_20260807_122221_000000000_fde47c0d2acc`，其完成后才启动测试策略 child
  `sa_20260807_122421_000000000_6d13535d3377`。

因此问题二的父级单 task 门禁已解决，模型可按任务关系自主选择并发或串行；同成员 tool scope
续用已按第 4.3 节冻结为任务008的独立修复。

## 5. 问题三：专家成员栏视觉层级异常

### 5.1 现象

成员栏是一条底部 sticky footer。截图中整条区域与 transcript/tool 内容发生叠压，外层背景渐变、
tabs 的透明 padding、每个成员按钮的灰白胶囊背景、阴影和激活态边框叠在一起，形成“背景里又套一层
div、按钮里再套白块”的观感。成员按钮与下方待办面板的视觉边界也不稳定。

### 5.2 源码依据

- `.agent-workspace__footer`使用 `position: sticky; bottom: 0`和由聊天背景到透明的渐变。
- `.agent-workspace__tabs`只有 4px padding，没有统一实体底板。
- `.agent-workspace__tab`自身使用半透明 elevated 背景、阴影和胶囊圆角；active tab 又叠加 accent
  背景与边框。

用户期望接近 WorkBuddy 的稳定成员行：整行使用统一白色底板，成员切换控件是同一层级中的轻量按钮，
不与 transcript 内容互相透叠。

## 6. 问题四：成员状态圆点语义不清

### 6.1 现象

截图中“代码审查专家”为黑/暗色圆点，“测试策略专家”和“发布风险顾问”为绿色圆点。界面没有图例，
暗色既像选中标记，又像离线或未开始，用户无法理解它与绿色的差别。

### 6.2 源码依据

`ExpertTeamSession.toolStatus`当前映射：

- `running` → running；
- `completed` → done（绿色）；
- `failed` → error（红色）；
- 其他所有值 → stopped（`var(--fg-faint)`暗色）。

后端还存在 `interrupted`状态，因此暗色至少可能代表 interrupted，也可能代表空值/未知值。截图发生前
同一代码审查子会话出现 tool scope 不一致的续用失败；暗色是否由该失败把既有 completed 状态改成
interrupted，仍需沿 meta 状态写入顺序确认。验收结束后的三个相关 child meta 均为 completed，说明
最终磁盘状态不能还原截图时的瞬时状态。

## 7. 验收补充：普通 task 越过子代理 effort 默认值

2026-08-08 使用普通聊天自然请求“请找一位独立的代码审查助手……”复验持久 `task`。父 Session
`20260808-093610.694512100-gpt-gpt-5.6-luna`，child
`sa_20260808_093757_000000000_e46018e7f081`。子会话约 5 分钟完成，产生约 10 轮 assistant 请求和
36 次内部工具调用；父会话只保留 task/wait 交付与主 Agent 后续 3 次只读核对，没有串入 child 工具历史。

本次同时发现新的成本控制缺口：环境配置 `subagent_effort = "medium"`，但父 Agent 生成的 task 参数
显式包含 `effort: "high"`，且没有同时提供 `model` 覆盖。`TaskTool` schema 已提示“只有覆盖模型时才
设置 effort”，但运行时 `effectiveProfile` 只在参数 effort 为空时使用配置默认值，因此模型生成的
`high` 被接受并覆盖了用户配置。这不是默认值自动升级，而是 schema 软提示与运行时约束不一致。

运行中 Composer 显示的 `↓ 6.8k token` 来自当前父 turn 的 completion token 累计，不代表完整计费
token；输入、缓存命中、child 请求和父 Agent 后续请求仍应由 usage/计费事件统计。不能据该数字推导
本轮总 token，但约 5 分钟、接近 12 步上限的广泛调查已能确认用户体感和资源消耗偏高。

任务014已按独立OpenSpec实现：三个子代理工具schema均不再暴露`effort`；旧参数继续宽松解析，但
共享`effectiveProfile`无论是否存在模型覆盖都只采用设置页解析的`subagentEffort`。精确回归确认配置
`medium`进入事件profile、Provider解析和持久child identity，空配置保持自动语义，模型覆盖、工具范围、
并发和持久化schema均未改变；`go test ./internal/agent -count=1`与OpenSpec严格校验通过。

真实Desktop复验已关闭：2026-08-08从当前worktree启动Wails dev，原生窗口虽然仍显示“登录已失效”，
但自定义Provider的`gpt/gpt-5.6-luna`实际可选、可发送并完成流式请求。普通自然开放任务由父Agent
自主派发`task`；父Session为`20260808-121931.925323700-gpt-gpt-5.6-luna`，child ref为
`sa_20260808_122159_000000000_8e8eb39a2fd1`。父JSONL原始参数只有`description/prompt/tools`，没有
`effort`；child meta记录`gpt/gpt-5.6-luna / medium`和`completed`，该profile同时进入Provider解析，
telemetry记录subagent来源9次真实请求。child实际完成读写、编辑和命令验证，job及artifact均完成；
父页面只显示外层task生命周期、父层复核和最终回答，没有child内部工具串页或专家历史入口，也没有
schema、tool-scope或profile错误。首次父层`complete_step`错误引用child diff证据被host拒绝后，Agent
自主补跑父层编译/smoke check并正常完成，不属于本effort合同缺陷。

## 8. 验收补充：自然调度、恢复与 WebView 稳定性

2026-08-08 使用 dev 环境和真实模型完成一轮不指定内部工具的自然场景验收。该轮只记录行为，未因
验收发现顺带修改运行逻辑。

### 8.1 普通聊天与临时并行

- 普通聊天父 Session `20260808-093610.694512100-gpt-gpt-5.6-luna`自然选择持久 `task`，child
  `sa_20260808_093757_000000000_e46018e7f081`完成后，父 transcript 只显示父 Agent 的工作更新、
  task/wait 交付和最终回复；child reasoning、消息和内部工具没有串入父页面。
- 切换其他会话再返回后，父结果仍在，普通聊天没有出现专家成员栏；子任务结果交付和父子页面隔离
  通过。
- “请并行让三个临时助手……”场景中，模型自然选择三个并发 `read_only_task`，父 Session
  `20260808-095425.311972400-gpt-gpt-5.6-luna`只接收三个结论，未产生新的 `subagents/sa_*.jsonl`
  和专家成员栏。这证明只读临时并行边界有效，但不等同于真实模型直接选择了 `parallel_tasks`；本轮
  未用强制工具措辞伪造该路径通过。

### 8.2 专家团并发、历史与恢复

专家团父 Session `20260808-094836.996382200-gpt-gpt-5.6-luna`自然并发启动两个不同持久 child：

- 代码审查专家 `sa_20260808_095039_000000000_55b45fe34ea7`；
- 测试策略专家 `sa_20260808_095039_000000000_850f2837528b`。

两个成员运行时显示黄色、完成后实时变绿；父页面没有 child 内部消息。分别点击两个头像均能打开完整
子会话历史和最终结论，`返回主会话继续对话`可以回到父 transcript。切换普通会话再返回以及退出并
重启 dev 应用后，父结论、两个绿色完成状态、成员栏和两份子历史均恢复。

### 8.3 中断与重复切换

- 普通会话在临时只读子任务运行约 31 秒后由用户停止。停止后用户消息、主 Agent 工作更新和工具卡
  立即保留，并直接显示中文 `本轮已中断`；未出现 `context canceled`，切换会话和重启后仍一致。
- 重启后又完成两轮接近人工速度的“普通会话 → 专家团父会话 → 子专家 → 返回”往返。父/子内容、
  成员状态和中断状态均未丢失，开发日志没有 `STATUS_BREAKPOINT`、panic、fatal 或 out-of-memory。
- 诊断采样中普通路径约 67 个 DOM 节点，专家团持久路径约 138 个；后两轮 used heap 从普通路径
  48.92 MB 到专家团加载中的 56.07 MB，再回落至持久路径 51.45 MB，没有观察到随往返单调增长。

### 8.4 仍需单独修复的间歇性点击问题

重启前的重复往返第 5 轮曾出现一次：首次点击“代码审查专家”后头像进入选中样式，但主内容仍停留在
父 transcript，且没有 `返回主会话继续对话`；再次点击同一头像立即恢复。重启后的首次复核与随后两轮
往返均未再次命中。

该现象暂定为“成员选择视觉状态与实际 workspace view 偶发不同步”，不是成员绑定消失、历史丢失或
WebView 崩溃。因尚未获得稳定复现和对应 trace，本轮只记录，不基于猜测修改。

下游评估关系。已确认的通用修复边界是：

- 已有running持久task时，另一task必须显式`independent: true`才允许并发；缺失意图返回中性
  `dispatch_decision_required`且不创建child。
- 依赖任务由父Agent先wait上游、检查并整理结果，再显式创建；宿主不自动排队或在child间传话。
- 每次持久turn暴露现有job ID作为`task_run_id`；`depends_on`只接受同父Session成功run，可跨父turn
  引用历史交付，但不改变各自计费归属。
- failed/interrupted/缺失/跨父Session依赖返回`dependency_not_satisfied`；四并发已满返回
  `capacity_wait_required`；均不显示红色child失败或成员头像。
- `parallel_tasks`继续是普通/单专家临时批量执行器，不纳入本合同。

需求、设计与实现拆分见OpenSpec `enforce-explicit-persistent-task-dispatch`和
