# 验收问题：中断父回合历史丢失与恢复错位

## 现象

真实专家团会话在用户中断父回合后，当前页面仍保留用户消息、主 Agent 输出和工具调用；切换会话或
重启应用后，父 transcript 却恢复为空。专家团 sidecar 和 child job 历史仍在，因此页面同时出现
欢迎页、已选中的历史会话和专家成员栏。

复现实例为父 Session `20260807-122125.508752500-gpt-gpt-5.6-luna`：父 JSONL 只剩 system
message，`.meta`仍记录原用户问题和一轮会话，`.expert.json`、checkpoint、已完成 child 和
`context canceled` child 均保留。

## 根因

`turnOrchestrator.runTurnWithRawDisplay`在显式用户取消且 runner 返回 `context.Canceled`时调用
`stripTurnMessagesAfter(startMessages)`。该函数删除本轮用户、assistant 和 tool messages，并强制
覆盖 JSONL。此逻辑来自 `66dadfc3`，目的是防止下一轮模型重复执行未完成 todo/工具；后续
`65f18ea6`又把截断结果强制落盘。

Frontend 的实时事件投影没有收到同等截断，因此取消后当前页面仍显示本轮内容；重载时才暴露磁盘
历史已经丢失。专家 sidecar 和 child job 使用独立持久化，进一步形成恢复状态错位。

## 已确认产品合同

- 用户中断只停止当前父 turn，并级联停止其 running child；不得删除已经产生的父/child历史。
- 持久 transcript保留原用户消息、assistant内容、reasoning、已发起工具和已有结果，并记录明确的
  interrupted边界。
- 下一轮模型必须知道上一轮被中断、工具可能已有副作用；未完成工作不得被视为成功或自动重放。
- 不完整工具链、todo/readiness和模型续聊安全必须在模型上下文层单独处理，不得通过删除用户历史
  实现。
- 重载后的父 transcript、会话选中态、专家 sidecar和 child状态必须一致；已有会话不得退化成欢迎页。

## 参考行为

本机 Codex真实 rollout在中断前持久化 reasoning、tool call和tool output，随后追加
`turn_aborted(reason=interrupted)`；不会删除整轮历史。Reasonix采用同一产品边界，但复用现有
Session、history projection和取消链路，不另建一套会话运行时。

## 验收场景

1. 普通会话在模型流式输出时停止，立即切换再返回：原用户消息和已产生内容仍在，并显示中断状态。
2. 普通会话在工具执行后停止，重启应用：工具调用、已有结果和中断边界仍可恢复。
3. 专家团父 turn有 completed child和running child时停止：running child变 interrupted，父历史、
   专家栏和两位 child历史均保留。
4. 中断后发送全新请求：模型收到中断上下文但不自动重做旧任务，旧 todo不阻塞新 turn final。
5. 中断后明确要求继续：模型可基于已保留结果继续，并对可能已执行的副作用保持谨慎。
