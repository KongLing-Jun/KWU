# 验收问题：专家会话返回双恢复与锚点漂移

## 状态与范围

该问题是独立 P1，也是当前 OpenSpec 验证中的一项已接受 WARNING：legacy→persisted 返回后的最终稳定位置
尚未通过。本交付范围不再继续修改滚动状态机，后续由专门变更处理。

`2da37ee4` 与 `f16026be` 保留。它们处理的是另一条已固证路径：向上 wheel 已建立中部锚点后，
虚拟总高收缩把物理视口 clamp 到新底部，以及 clamp 候选的最新 offset/identity 同步。本页记录的
问题发生在导航返回后的 legacy→persisted 恢复阶段，不证明上述两个提交无效，也不由回滚它们解决。

## 用户影响

长专家团会话返回时，正文和锚点 identity 均存在，但视口可能从离开前的阅读段落跳到更早或更后的
内容。错误位置会继续写入 Session cache，影响下次返回。当前证据没有数据丢失、崩溃、安全问题或
持久格式损坏，因此定级为 P1 功能正确性问题。

## 精确复现

1. 使用 `f16026be` 的 clean Wails 构建，打开证据中的长专家团父会话。
2. 明确滚到 transcript 底部。
3. 在 transcript 内只执行一次原生向上 wheel；该次证据满足：
   - 一个 `wheel.begin`；
   - 零个 `wheel.restart`；
   - 一个 `wheel.expire`；
   - 实际 `deltaY=-1083.333203125`。
4. 等待物理视口稳定。离开前 Session cache 为问题 q5、offset `-606.2000`，导航前没有新的用户输入。
5. 打开模型广场并确认 Transcript 卸载，再返回同一会话。
6. 等待至少 2.5 秒，比较返回前后视觉内容，并检查 trace 中的恢复与 cache write。

本次复现中，离开前截图位于上一轮长回复第 6–9 项附近；返回稳定后跳到下一轮用户问题及回复开头，
不是同一或近似阅读位置。

## 已证时序与根因边界

1. 返回时使用 semantic anchor，不是 bottom fallback；两轮恢复始终使用同一 opaque anchor、问题索引 5
   和初始 offset `-606.2`，因此不是 identity 丢失。
2. 页面先提交 `team-legacy` presentation，在虚拟 row 33 对同一目标执行五帧恢复：前三帧 DOM 未就绪，
   第四、第五帧成功。
3. sidecar 到达后提交 `team-persisted` presentation，目标映射到虚拟 row 39，又执行一套五帧恢复：同样
   前三帧失败，第四、第五帧成功。
4. 当前恢复任务只要任一帧成功，就在第五帧结束时清除 `pendingScrollAnchor`；它不验证最终实测 offset，
   也不等待虚拟测量和范围稳定。
5. pending 清除后，非用户程序化滚动不再受写回冻结保护。persisted 第五帧结束后的 4ms、19ms 分别
   把同一锚点 offset 写成 `-579.8` 和 `-42.2`，最终位置因此漂移。

结论：固定五帧完成条件会在布局尚未稳定时清除 pending，并重新开放 cache 写回；随后晚到的非用户
程序化 scroll 会覆盖已经恢复的 canonical offset。legacy 与 persisted 顺序启动两套恢复是已观测时序，
但“缺少单一 restore owner”只是后续设计假设，当前证据没有证明它是唯一根因或充分修复。

## 尚未证明的边界

- trace 没有给每次晚到 scroll 标出唯一物理发起者，不能断言某一个 TanStack measurement、
  `ResizeObserver` 或 DOM reflow 单独导致漂移。
- DEV trace 中存在 effect 重挂，但不能据此断言 StrictMode 是双恢复的必要条件；产品上已确定的是
  legacy→persisted 两个 presentation path 连续恢复。
- 单次样本只能证明“固定五帧且任一成功即完成”在该序列不充分，不能推导所有设备所需的固定帧数。
- DEV Wails 已真实复现；正式生产 bundle 的复现概率仍需后续独立变更验收。

## 与 clamp 问题的区别

`fedfbef` 证据中，位置在导航前已经丢失：wheel 前三帧依次捕获 q5 的 `295.4`、`155.4`、`47.4`，
第四帧虚拟总高收缩后浏览器把 `scrollTop` clamp 到新 max，旧实现随即把 cache 写成 bottom；返回时没有
semantic restore。`2da37ee4` 与 `f16026be` 针对这条 capture-side 路径，并有精确旧红新绿回归。

本页问题则在离开前已稳定保存 q5/`-606.2`，返回后才因两套 restore 与过早解除写回冻结而漂移。
两者必须分开设计和验收。

## 后续独立变更建议

后续优先评估“跨 presentation 的单一语义恢复事务”，并与其他满足稳定完成条件的方案比较；不能在没有
新红测和反事实证据时把它预设为唯一实现，也不应继续增加局部 RAF guard。候选设计约束如下：

- 每个 semantic view 同时只有一个 restore owner/generation。
- canonical target 在事务期间保持 `{viewKey, stableQuestionIdentity, offset}`；row 33/39 只是不同虚拟器
  对同一目标的临时解析结果。
- legacy→persisted 只转移 presentation resolver：取消旧 RAF，由新虚拟器接管同一事务，不重新创建
  或重新解释目标。
- active restore 期间，非用户 scroll 只更新几何和 UI，不得提交 Session anchor。
- 恢复完成必须同时满足目标 DOM 已挂载、identity 匹配、实测 offset 在容差内，并在最近一次虚拟测量/
  范围变化后连续稳定；仍保留明确硬上限。
- 超限时保留 canonical target并记录 incomplete，不得把恢复副作用当作用户新位置写回。
- wheel、pointer、touch、滚动键、明确 reveal、跨 view 和卸载以 generation 原子取消旧事务。
- 不修改 wire、持久格式、全局虚拟器策略或 `2da37ee4`/`f16026be` 的 wheel candidate 行为。

## 后续验收矩阵

| 场景 | 必须证明 |
| --- | --- |
| legacy only / persisted only | 原 anchor 与 offset 恢复正确 |
| legacy→persisted，sidecar 在第 1–5 帧任意时刻到达 | 始终只有一个 owner，旧 RAF 不再写入 |
| 前三帧 DOM 缺失、第四帧出现 | 不因一次成功过早完成 |
| 第五帧后仍有测量和范围变化 | cache 保持 canonical target，直到真实稳定 |
| row index 从 33 变为 39 | identity 与 offset 不变 |
| 大负 offset、正 offset、零 offset | 均在定义容差内恢复 |
| history identity replacement | canonical identity 重映射，offset 不变 |
| 用户输入、reveal、跨 view、卸载、StrictMode | 旧 generation 立即失效 |
| anchor 删除 | 一次有界 fallback，不循环 |
| true bottom、普通 transcript | 既有行为不回归 |
| 原生生产验收 | 单次 wheel→稳定→模型广场→返回，DOM offset 与视觉内容一致 |

确定性自动化应构造：legacy 前三帧失败、后两帧成功，随后 persisted 重挂重复该序列，并在第二套
第五帧后产生晚到测量；旧实现最终写 `-42.2`，新实现保持并稳定恢复 `-606.2`。
