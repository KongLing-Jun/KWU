## 2. 目标与预期产物

在保留安装前一次在线授权的前提下，让安装阶段遵循 OSS→GitHub 的有序授权：

- OSS 成功取得 manifest 后成为唯一权威；完全匹配即授权，明确不匹配即拒绝。
- 只有 OSS manifest 获取、解析或网络访问不可用时才尝试 GitHub。
- GitHub 作为实际采用源时也必须完整匹配版本、当前平台、SHA256 和大小。
- 所有配置源不可用时拒绝本次安装但保留已通过本地完整性校验的缓存。
- 本地缓存损坏或实际采用源明确拒绝时删除缓存。

## 4. 强制技术契约

### 4.1 授权结果必须结构化

- 在线判定必须显式表达 `authorized`、`unavailable`、`rejected` 三种结果。
- 可使用内部枚举加结果结构，或可由 `errors.As` 判定的内部错误类型；结果须携带实际源
  与原始原因，具体命名由实现者决定。
- `readCurrentVerifiedCachedUpdate` 必须直接按类型/结构决定是否失效缓存。
- 生产代码不得通过 `err.Error()`、`strings.Contains`、错误前缀或其他文本解析区分
  “不可用”和“明确拒绝”；测试也不得以错误文本作为分类证据。
- 多源均不可用时保留各源失败原因用于最终诊断，但聚合文本不能成为控制流契约。

### 4.2 有序源语义

- manifest 获取失败（超时、DNS/连接、非 200、读取、JSON、无合法版本）是
  `unavailable`，继续下一源；父 context 已取消时停止继续请求。
- 成功解析 manifest 后，缺少当前平台资产，或版本、SHA256、大小不匹配均是
  `rejected`，立即停止，不得访问或采用后续源。
- 首个成功解析且四项完全匹配的源是 `authorized`，立即停止；后续源状态不再相关。
- 无源配置、HTTP client 无法创建和所有源不可用均拒绝本次安装并保留有效缓存。
- 本地 metadata/channel/platform/file/SHA256 完整性失败仍在联网前拒绝并删除缓存。
- installer/apply 返回错误不改变本任务现有缓存策略，不扩展到安装器生命周期重构。

| 场景 | 源访问 | 安装调用 | 缓存结果 |

| 两个源均配置为匹配 | OSS 授权后短路 GitHub | 1 次 | 保留，不提前删除 |
