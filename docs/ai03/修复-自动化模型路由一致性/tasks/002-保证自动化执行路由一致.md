## 目标

让自动化任务的显式 `model + billingSource` 成为其 Controller build 的权威输入：复用 session 只恢复历史和其他会话状态，不能覆盖任务 route。Controller 就绪后、任何运行副作用前再做一次精确一致性检查，残余 mismatch 必须 blocked 且不得调用模型或产生计费。

实施前先复述目标、根因证据、允许范围、保留行为和禁止范围；如需要改变持久化 schema、计费 resolver、普通 session 语义或采用守卫后自动重建，停止并报告。

## 交付物

1. 为 tab Controller 调度/构建增加一个仅属于本次 build generation 的可选显式 route 输入，值为完整 `modelbilling.BillingRouteSelection`；不得把它变成持久化 task/tab schema 或长期可变全局状态。
2. route-aware 自动化 topic 新建 tab 时，把任务 route 传入对应异步 build；普通 `openTopicTab...` 继续传 nil。
3. `setModelRouteForTabWithPersistence` 在 `tab.Ctrl == nil` 的 rebuild 路径把目标 route 作为显式 build 输入，覆盖应用启动时普通 session restore 已先开始、自动化随后 wait-then-repair 的场景。
4. 显式 route build 使用该快照的 source 加载 config，并使用该快照 model 构建 Controller：跳过 session model、topic model和默认 model 覆盖；不得调用会换模的 subscription/config fallback。显式 model 在该 build config 中无法精确解析或不满足既有 route 可用条件时，build 失败。
5. 无显式 route 的普通 session build 保持当前优先级、legacy 规范化、fallback、通知和 `.meta` 恢复行为。
6. build 成功提交 tab 状态时，`tab.model`、`tab.billingSource` 和 Controller 构造参数来自同一 build-local route，并继续受现有 generation/cancel 检查保护。
7. route-aware opener 返回 existing controller-missing pending tab 时，runner 不得只依据等待前字段决定 repair：先等待当前 generation，完成后重新精确比较 route；若 `.meta` 覆盖造成 mismatch，调用一次既有原子 route repair 并等待显式 repair build。若等待因该 generation 的 `StartupErr` 或 `Ready` 但无 Controller 而失败，也对本次已验证的 task route 执行一次显式 repair；context cancel/deadline 或 tab 仍纯 pending 的 timeout 直接返回。已有可用 Controller 或其他非 pending 状态沿用现有判断。
8. runner 在最终 `waitAutomationTopicController` 返回后、改变审批模式/准备 assist/执行 turn 前，锁下读取 tab 的最终 `model + billingSource` 并与本次任务 route 精确比较。不同则返回 `RunStatusBlocked`；该最终 guard 不自动重建，不调用 `RunCapabilityTurn`，不触发 gateway 或计费。
9. 增加回归测试覆盖异步旧 session 覆盖、字段预先匹配但 `.meta` 不同的 pending build、旧 route 启动失败后 task route repair、cancel/timeout 不 repair、controller-less repair、普通 session 恢复、同 source 不同 model mismatch 和调用前零副作用守卫。

## 根因与事实证据

- `desktop/automation_runner.go:30-53` 先解析 task route、绑定 topic、做构建前 repair，再等待 Controller；当前等待后没有 route 检查。
- `desktop/automation_runner.go:64-97` 在 Controller 就绪后改变审批状态、准备 assist 并调用 `RunCapabilityTurn`。
- `desktop/automation_runner.go:149-165` 的 repair 只比较 build 前 tab 字段；异步 build 可以在之后改变 model。
- `desktop/automation_topic.go:12-53` 已把 route 传给 project/global route-aware opener。
- `desktop/tabs.go:1527-1710` route-aware opener 用任务 route 初始化 tab，但启动 build 时没有把 route 作为不可变 build 参数。
- `desktop/tabs.go:1558-1574,1581-1617` 遇到 existing session/tab 会直接返回并丢弃传入 route；pending 普通 restore 仍可能在返回后覆盖 tab model。
- `desktop/tabs.go:2606-2684` 的调度以 generation/cancel 管理 build，适合承载 build-local 输入。
- `desktop/tabs.go:3016-3021` 无条件从 session `.meta` 恢复可解析 model，覆盖初始 task model。
- `desktop/tabs.go:3031-3053` 对 subscription 和 config 执行 fallback，可把显式任务 route 改为其他模型。
- `desktop/tabs.go:3072-3101` 先把最终 model 写入 tab，再用 `tab.billingSource` 构建 Controller；显式 route 必须让这两者来自同一快照。
- `desktop/app.go:7880-7896` 的 controller-less 模型切换通过 `scheduleTabControllerBuild` 重建；它同样会重新读取 session model，是复用 session 自动化 repair 的可达路径。
- 已记录运行证据表明 manifest 为 `kwu/deepseek-v4-flash + subscription_pool`，实际 turn/账本却为 `gpt-5.6-luna + subscription_pool`，证明构建前比较不足。

## 必须保留的行为

- 同一 session 的历史、expert、effort、scene、tool approval、路径和 topic 继续恢复；只在显式 route build 时禁止模型身份覆盖。
- tab build generation、取消、shared host、active work 防护和原子 Controller 替换保持现有合同。
- 应用启动时已经开始的普通 restore 可先完成；自动化绑定后对所有 controller-missing pending build 都先等待并重新比较，必要时调用一次既有 repair，且 repair build 必须携带显式 route。
- 已有/失败 tab 的构建前 repair 行为继续存在；最终 guard 只是不可绕过的最后防线。
- `NewConversationEachRun`、global/project actor、topic 持久化和 run manifest 的现有流程不变。
- 普通用户在 task session 中手动选模型只改变该 session；下次自动化按持久化 task route repair。
